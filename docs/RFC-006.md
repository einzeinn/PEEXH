# RFC-006 — Evaluation Framework and Baseline Benchmarking

**Status:** Proposed  
**Type:** Evaluation / Research / Quality Assurance  
**Scope:** Backend (`backend/evaluation/`), Test Data, Documentation  
**Governing Phase:** Phase 5 (Evaluation)  

---

## 1. Summary

This RFC implements **Phase 5: Evaluation** of the PEEXH roadmap. It establishes a reproducible, evidence-based evaluation framework to prove that PEEXH provides measurable improvement over raw speech-to-text output for dysarthric speakers.

The framework provides:
1. **Baseline STT Capture**: Recording raw AssemblyAI transcriptions of dysarthric speech samples without any PEEXH agent processing.
2. **PEEXH Interpretation Comparison**: Running the same audio samples through the full PEEXH agent stack and recording final interpreted phrases.
3. **Repeated-Attempt Testing**: Simulating multi-utterance sessions to evaluate the impact of the RFC-005 adaptive memory loop across repeated identical attempts.
4. **Personalization Tests**: Verifying that submitting a correction measurably improves subsequent interpretation accuracy for that correction pair.
5. **Latency Profiling**: Measuring end-to-end latency from speech stop to `agent_decision` event, segmented by pipeline stage.
6. **Failure Case Documentation**: Cataloguing failure examples where PEEXH underperforms or the agent falls back to `REQUEST_REPEAT`.

---

## 2. Motivation

PEEXH is built on a claim: applying a deterministic confidence policy and personal speech memory on top of a general STT model produces meaningfully better communication outcomes for people with dysarthria than raw transcription alone.

Without an evaluation framework, this claim is unverifiable. A submission or demo without measurement evidence is anecdotal. Specifically:

- AssemblyAI Realtime produces phonetically mangled transcriptions for dysarthric speakers. How mangled?
- PEEXH agent interpretation improves on those transcriptions. By how much?
- RFC-005 memory learning accelerates correct resolution on repeated utterances. Is that measurable?
- The full pipeline adds latency. Is it within an acceptable conversational threshold?

Phase 5 answers these questions with licensed or public speech samples, a reproducible evaluation script, and documented results that can accompany a demo or technical submission.

> **Core Principle Alignment:**  
> *"LLM interprets. PEEXH decides. User controls. Memory personalizes."*  
> Evaluation proves each step adds value.

---

## 3. Scope and Non-Goals

### In Scope
- A standalone evaluation module (`backend/evaluation/`) with scripts, data loaders, and result formatters.
- A curated test dataset of dysarthric-speech phonetic transcription patterns, sourced from:
  - Publicly available dysarthric speech corpora (e.g., TORGO, UASpeech — text prompts only, no audio stored).
  - Hand-crafted representative phonetic distortion samples consistent with spastic, flaccid, and ataxic dysarthria patterns.
- A `BaselineCapture` runner: submitting raw transcript strings to AssemblyAI mock (or live) and recording raw output without agent involvement.
- A `PeexhEvaluator` runner: running the same transcript strings through the full `PeexhAgent` stack.
- A `MemoryLoopEvaluator`: simulating two-pass utterance sessions (first pass: no memory, second pass: after injecting a correction pair via `record_correction`).
- Word Error Rate (WER) computation between raw STT output and the intended phrase.
- Intent Match Rate (IMR): a binary accuracy score — whether `AgentDecision.primary_phrase` exactly or semantically matches the target intended phrase.
- Latency measurements: total pipeline duration, and per-stage timing for STT adapter, LLM interpreter, confidence scorer, and memory retrieval.
- A Markdown evaluation report template, auto-populated by the evaluation script.
- Documentation of failure cases and edge conditions in `docs/11-Research.md`.

### Out of Scope
- Storing or transmitting any real audio files (audio data prohibition per RFC-005, Section 6).
- Recruiting real human subjects for live evaluation (deferred to future research phases).
- Fine-tuning or modifying the underlying AssemblyAI or LLM model weights.
- Automated CI pipeline integration for evaluation (evaluation runs are on-demand, not per-commit).
- Statistical significance testing (sample sizes in V1 are indicative, not publication-grade).

### 5.2 Evaluation Dataset Schema (`samples.json`)

Each sample defines a realistic dysarthric phonetic distortion scenario:

```json
[
  {
    "id": "SAMPLE-001",
    "dysarthria_type": "spastic",
    "raw_stt_transcript": "i ned wtr",
    "intended_phrase": "I need water",
    "stt_confidence": 0.62,
    "notes": "Final plosive and mid-vowel reduction. Consistent TORGO-style pattern."
  },
  {
    "id": "SAMPLE-002",
    "dysarthria_type": "ataxic",
    "raw_stt_transcript": "ple cal hel",
    "intended_phrase": "please call help",
    "stt_confidence": 0.55,
    "notes": "Initial fricative deletion and syllable boundary blurring."
  }
]
```

Fields:
- `id`: Unique identifier for result tracing.
- `dysarthria_type`: Clinical category (`spastic`, `flaccid`, `ataxic`, `mixed`).
- `raw_stt_transcript`: Simulated or captured raw STT output string.
- `intended_phrase`: The speaker's actual intended message (ground truth).
- `stt_confidence`: Simulated STT acoustic confidence score (0.0–1.0).
- `notes`: Annotation of the phonetic distortion pattern.

### 5.3 Metrics Definitions

#### Word Error Rate (WER)

Standard ASR evaluation metric. Defined as:

$$\text{WER} = \frac{S + D + I}{N}$$

where $S$ = substitutions, $D$ = deletions, $I$ = insertions, and $N$ = number of words in the reference (intended phrase).

WER is computed for:
- **Baseline WER**: `raw_stt_transcript` vs `intended_phrase`.
- **PEEXH WER**: `AgentDecision.primary_phrase` vs `intended_phrase`.

#### Intent Match Rate (IMR)

Binary accuracy metric specific to PEEXH's use case:

$$\text{IMR} = \frac{\text{Correct Interpretations}}{\text{Total Samples}} \times 100\%$$

A sample is scored as correct (`1`) if:
- `AgentDecision.action == PROPOSE_PHRASE` and `primary_phrase` matches `intended_phrase` (case-insensitive, punctuation-stripped), OR
- `AgentDecision.action == SHOW_CANDIDATES` and `intended_phrase` appears in `candidates`.

#### Latency Stages

Each evaluation run records wall-clock durations for:

| Stage | Description |
|---|---|
| `memory_retrieval_ms` | Time for `MemoryStore.retrieve_matches()` to return |
| `llm_interpret_ms` | Time for `Interpreter.interpret()` to return |
| `scorer_ms` | Time for `ConfidenceScorer.score_and_decide()` to return |
| `total_pipeline_ms` | End-to-end from `process_transcript()` call to `AgentDecision` |

Target: `total_pipeline_ms < 1500ms` for cloud LLM path; `< 200ms` for mock path.

#### Memory Loop Delta

For `MemoryLoopEvaluator`, the delta is reported as:

- **Pass 1 WER**: No prior memory, first-time utterance.
- **Pass 2 WER**: After `record_correction()` injection, same utterance repeated.
- **Delta**: Pass 1 WER − Pass 2 WER. A positive delta indicates memory-driven improvement.

### 5.4 EvaluationRunner (`runner.py`)

```python
class EvaluationRunner:
    """Orchestrates baseline, PEEXH, and memory-loop evaluation passes."""

    def __init__(
        self,
        dataset_path: str,
        use_mock_interpreter: bool = True,
        use_mock_memory: bool = True,
    ) -> None: ...

    async def run_baseline(self) -> List[BaselineResult]: ...
    async def run_peexh(self) -> List[PeexhResult]: ...
    async def run_memory_loop(self) -> List[MemoryLoopResult]: ...
    async def run_all(self) -> EvaluationSummary: ...
    def export_report(self, output_path: str) -> None: ...
```

## 6. Privacy, Security & Data Policy

1. **No Audio Storage**: Evaluation uses text-only phonetic transcription strings. No audio files, waveforms, or speaker recordings are stored or transmitted.
2. **Synthetic Dataset**: V1 samples are hand-crafted or derived from the textual phonetic patterns published in public research corpora (TORGO, UASpeech papers). No personally identifiable speaker data is included.
3. **Isolated Execution**: Evaluation runs are performed locally or in CI against the mock interpreter and mock memory store by default. Cloud LLM calls are opt-in via `--use-cloud` flag.
4. **No User Data**: Evaluation does not interact with any real user's `speech_corrections` or `phrase_frequencies` tables in Supabase.

## 7. Implementation Tasks

1. **Dataset Preparation**:
   - Research and document at least 30 representative dysarthric phonetic distortion patterns across spastic, flaccid, ataxic, and mixed types.
   - Create `backend/evaluation/data/samples.json` with ground-truth `intended_phrase` for each.
2. **Metrics Module**:
   - Implement `metrics.py`: WER calculation (using edit distance), IMR binary scoring, latency aggregation.
3. **Baseline Capture**:
   - Implement `baseline.py`: `BaselineCapture` computing WER of `raw_stt_transcript` against `intended_phrase` without any agent involvement.
4. **PEEXH Evaluator**:
   - Implement `peexh_eval.py`: `PeexhEvaluator` using `PeexhAgent` with `MockInterpreter` (default) or `CloudLLMInterpreter` (opt-in), recording all result fields and latency breakdowns.
5. **Memory Loop Evaluator**:
   - Implement `memory_loop.py`: `MemoryLoopEvaluator` performing two passes per sample, injecting a correction pair via `MockMemoryStore.record_correction()` between passes, and reporting WER delta.
6. **Runner & Report**:
   - Implement `runner.py`: `EvaluationRunner` orchestrating all evaluators.
   - Implement `report.py`: Generating Markdown and JSON evaluation reports to `backend/evaluation/reports/`.
7. **Automated Tests**:
   - `test_metrics.py`: Unit tests for WER calculation correctness (zero WER, full WER, partial substitutions) and IMR edge cases.
   - `test_baseline.py`: Verify `BaselineCapture` correctly computes WER for known sample pairs.
   - `test_peexh_eval.py`: Verify `PeexhEvaluator` correctly records `AgentDecision` fields and latency.
   - `test_memory_loop_eval.py`: Verify `MemoryLoopEvaluator` produces a positive `memory_delta` after correction injection on a known sample.
8. **Documentation**:
   - Update `docs/11-Research.md` with evaluation findings and failure case catalogue.
   - Update `docs/12-Changelog.md` with RFC-006 entry.

## 8. Acceptance Criteria

1. **Baseline vs PEEXH Improvement**: On the 30+ sample dataset, PEEXH Avg WER is measurably lower than Baseline Avg WER (target: ≥10% relative improvement).
2. **Intent Match Rate**: PEEXH achieves ≥60% IMR on the curated dataset when using the `MockInterpreter`, confirming the agent architecture is sound.
3. **Memory Loop Delta**: `MemoryLoopEvaluator` produces `memory_delta > 0` for all samples where a correction pair exactly matches the test utterance, confirming RFC-005 learning hooks fire correctly.
4. **Latency Compliance**: Mock pipeline `total_pipeline_ms` consistently remains below 200ms. Cloud LLM pipeline `total_pipeline_ms` remains below 1500ms on the evaluation machine.
5. **No Audio Data**: The evaluation module contains no binary audio files. All evaluation inputs are JSON text strings. Verified by reviewing `backend/evaluation/data/` contents.
6. **Regression Safety**: All existing 52 backend tests continue to pass after adding the evaluation module. Frontend `npm run build` remains clean.
7. **Report Output**: `EvaluationRunner.export_report()` produces a valid, non-empty Markdown file and JSON file to `backend/evaluation/reports/`.
8. **Language**: All code, scripts, data annotations, and documentation are strictly in English.

## 9. Supersession & Relation to Previous RFCs

- **Builds on RFC-003**: RFC-003 introduced the `ConfidenceScorer` and the Observe → Interpret → Score → Decide pipeline. RFC-006 evaluates whether that pipeline actually improves interpretation accuracy over the raw STT baseline.
- **Builds on RFC-005**: RFC-005 implemented the adaptive memory loop. RFC-006 quantifies the memory loop's impact via the `MemoryLoopEvaluator` and confirms RFC-005's core claim: repeated utterances after correction injection resolve with higher accuracy and lower WER.
- **Informs Phase 6**: Evaluation findings and documented failure cases from RFC-006 will directly inform the demo polish strategy in Phase 6, identifying the strongest demonstrable improvement scenarios and the honest boundaries of V1.
