# RFC-004 — Confirmation UX and Communication Output

**Status:** Revised
**Type:** Feature / API Contract / Accessibility
**Scope:** Frontend and Backend
**Governing Phase:** Phase 3 (Confirmation UX)

---

## 1. Summary

This RFC implements Phase 3 of the PEEXH roadmap. It completes the user-controlled portion of the communication loop after RFC-003 has produced an `AgentDecision`.

The feature provides:

1. Explicit confirmation for high-confidence phrase proposals.
2. Accessible selection, correction, and repeat actions for medium-confidence candidate sets.
3. A recovery path for low-confidence decisions, including optional manual phrase entry.
4. Backend-authoritative confirmation state transitions and a `communication_ready` WebSocket event.
5. A large-text communication view and optional browser TTS with replay control.

The resulting loop is:

```text
Agent decision (HIGH / MEDIUM / LOW)
  -> Backend enters AWAITING_CONFIRMATION for all three action types
  -> User confirms, selects, corrects, or requests a repeat
  -> Backend validates the user action and transitions state
  -> Frontend displays and optionally speaks the confirmed phrase
```

> **Key invariant:** Every `agent_decision` event, regardless of confidence level, places the agent in `AWAITING_CONFIRMATION`. The agent never transitions to `IDLE` autonomously on a decision — only an explicit user `request_repeat` message does.

---

## 2. Motivation

RFC-003 intentionally stops at `AWAITING_CONFIRMATION`. Its interpretation is a suggestion, not the user's final intent. Without an explicit confirmation interaction, PEEXH would violate its core principle: "LLM interprets. PEEXH decides. User controls."

Phase 3 makes the interaction useful in a face-to-face conversation while preserving recovery from uncertain speech:

- A high-confidence phrase remains a quick, one-tap confirmation, never an automatic communication.
- A medium-confidence result offers two or three large candidate controls and a manual correction route.
- A low-confidence result asks the user to repeat and permits manual entry when repeating is not practical.
- Only a user-confirmed, user-selected, or user-entered phrase can be presented as ready to communicate or passed to TTS.

---

## 3. Scope and Non-Goals

### In Scope

- Confirmation, candidate selection, manual correction, and repeat controls.
- Agent state transitions from `AWAITING_CONFIRMATION` to `CONFIRMED` or `IDLE`.
- WebSocket request and event contracts for resolving an agent decision.
- Large-text confirmed-message display.
- Browser `SpeechSynthesis` playback and replay when TTS is enabled and supported.
- Automated tests for validation, state transitions, protocol events, and accessible UI states.

### Out of Scope

- Persisting corrections, learning from corrections, memory retrieval, or database schema changes. These belong to Phase 4.
- Dedicated cloud TTS providers, voice cloning, or audio-file generation.
- Automatic TTS playback before a user action.
- Automatic communication of any phrase.
- Translation, emergency features, medical claims, authentication, or unrelated navigation.

---

## 4. Product and Safety Rules

1. A phrase is not a final message until the user explicitly confirms, selects, or enters it.
2. `PROPOSE_PHRASE` must render a confirm action and a correction action. It must not auto-advance to communication.
3. `SHOW_CANDIDATES` must render two or three candidate buttons, a manual correction action, and a repeat action.
4. `REQUEST_REPEAT` must not present an unverified phrase as communicable. The agent enters `AWAITING_CONFIRMATION` with a repeat prompt and a manual-entry option. It does **not** automatically return to `IDLE`; only the user's `request_repeat` WebSocket message causes that transition.
5. The backend must never autonomously leave `AWAITING_CONFIRMATION` — all exits require a user-initiated control message.
6. User-entered correction text is authoritative after confirmation. It is not reinterpreted or silently normalized beyond trimming surrounding whitespace.
7. TTS is opt-in per playback. The confirmed phrase must remain visible regardless of TTS availability.
8. Phase 3 must not retain corrections after the active WebSocket session ends.

## 5. State Machine and Protocol

### 5.1 State Transitions

`PeexhAgent` is the sole authority for all state transitions:

```text
IDLE / LISTENING / INTERPRETING / DECIDING
  -> agent emits agent_decision (any action: PROPOSE_PHRASE, SHOW_CANDIDATES, REQUEST_REPEAT)
  -> AWAITING_CONFIRMATION

AWAITING_CONFIRMATION
  -> user sends confirm_proposal  (valid only for PROPOSE_PHRASE decision)   -> CONFIRMED
  -> user sends select_candidate  (valid only for SHOW_CANDIDATES decision)  -> CONFIRMED
  -> user sends submit_correction (valid for any decision)                   -> CONFIRMED
  -> user sends request_repeat    (valid for any decision)                   -> IDLE

CONFIRMED
  -> user starts new speech session -> IDLE -> LISTENING
```

**Critical alignment note:** `REQUEST_REPEAT` is an `AgentAction` (the backend's output decision for LOW confidence), not a state. All three `AgentAction` values result in the agent entering `AWAITING_CONFIRMATION`. The user-initiated `request_repeat` WebSocket message is the only mechanism that explicitly returns the agent to `IDLE` from `AWAITING_CONFIRMATION`.

The backend must reject any resolution message unless the agent is in `AWAITING_CONFIRMATION`. A rejected request emits an `error` event and must not emit `communication_ready`.

### 5.2 WebSocket Lifecycle

After sending `agent_decision`, `/ws/speech` must keep the WebSocket open while the agent awaits a user response. The frontend must not close the connection on receipt of that event.

The existing `start`, `stop`, and binary audio-frame messages remain unchanged. The following control messages are added after an `agent_decision` event.

#### Client to Server

```json
{ "type": "confirm_proposal" }
```

Valid only for `PROPOSE_PHRASE`. The backend confirms the current `primary_phrase`.

```json
{ "type": "select_candidate", "phrase": "I need some water" }
```

Valid only for `SHOW_CANDIDATES`. `phrase` must exactly match one candidate in the active decision.

```json
{ "type": "submit_correction", "phrase": "I need to use the bathroom" }
```

Valid for `PROPOSE_PHRASE`, `SHOW_CANDIDATES`, and `REQUEST_REPEAT`. `phrase` must be non-empty after trimming and must not exceed 500 characters. The submitted text becomes the confirmed message exactly as entered after surrounding whitespace is trimmed.

```json
{ "type": "request_repeat" }
```

Valid for any active decision in `AWAITING_CONFIRMATION`. This is the **only** user action that transitions the agent from `AWAITING_CONFIRMATION` back to `IDLE`. The backend clears the active decision and emits `repeat_requested`. It is the user's explicit signal that they want to speak again or abandon the current decision.

#### Server to Client

```json
{
  "type": "communication_ready",
  "phrase": "I need some water",
  "source": "proposal"
}
```

`source` is one of `proposal`, `candidate`, or `correction`. This event is emitted only after a valid user action has moved the agent to `CONFIRMED`.

```json
{ "type": "repeat_requested" }
```

This event confirms that the active decision has been discarded and the user may start a new attempt.

Invalid controls or invalid state transitions use the existing error shape:

```json
{ "type": "error", "message": "...", "code": "INVALID_AGENT_RESPONSE" }
```

### 5.3 Domain Models

Add typed Pydantic models in `backend/app/models/agent.py` for:

- `ConfirmProposalMessage`
- `SelectCandidateMessage`
- `SubmitCorrectionMessage`
- `RequestRepeatMessage`
- `CommunicationReadyEvent`
- `RepeatRequestedEvent`
- `ConfirmedPhraseSource` enum with `PROPOSAL`, `CANDIDATE`, and `CORRECTION`

The orchestrator must retain only the active `AgentDecision` in process memory for the current socket session. It must clear it after a successful confirmation, a repeat request, reset, disconnect, or error that ends the session.

## 6. Frontend Interaction Specification

### 6.1 Decision Controls

The speech screen uses the `agentDecision` from `useSpeechStream` to render the following actions. All three decision types land the agent in `AWAITING_CONFIRMATION`; the table describes the UI controls rendered for each:

| AgentAction | Primary controls | Recovery controls |
| --- | --- | --- |
| `PROPOSE_PHRASE` | Confirm phrase | Correct phrase, Speak again |
| `SHOW_CANDIDATES` | One large button per candidate | Correct phrase, Speak again |
| `REQUEST_REPEAT` | Speak again (`request_repeat` message) | Enter phrase manually (`submit_correction`) |

**`REQUEST_REPEAT` UI note:** The frontend must present this state as a prompt to speak again, not as an error. "Speak again" sends `request_repeat` → `IDLE`. "Enter manually" opens the correction input → `submit_correction` → `CONFIRMED`. The backend never auto-exits this state.

Candidate controls must be semantic `button` elements, not clickable `div` elements. Confirmation, manual submission, and repeat must send the corresponding WebSocket control message and enter a pending state until the server responds.

### 6.2 Correction

Correction mode contains a labeled text input, a visible submit button, and a cancel action returning to the unresolved decision. It must preserve the raw transcript and candidate list in the interface while open so the user can orient themselves.

### 6.3 Communication View

When `communication_ready` arrives:

- display the exact confirmed phrase in a dedicated large-text region with high contrast;
- offer a text-labeled `Speak message` button when browser TTS is enabled and supported;
- offer a text-labeled replay control after playback starts;
- provide a `Start new message` action that clears local confirmation state and begins a new recording flow;
- do not play audio automatically.

Browser `SpeechSynthesis` is the Phase 3 implementation of TTS, consistent with TD-010. TTS availability is controlled by a public frontend feature flag and must fail gracefully when unavailable.

### 6.4 Accessibility

- All action controls require visible text labels and keyboard operation.
- Candidate, confirmation, correction, repeat, TTS, and new-message controls must have at least a 44 by 44 CSS pixel target.
- The pending, error, and confirmed-message regions must use appropriate live-region semantics without repeatedly announcing unchanged transcript content.
- Focus moves to the confirmed-message heading after a valid `communication_ready` event.
- The correction input receives focus when correction mode opens.
- Color is not the only indicator of confidence or confirmation state.

## 7. Implementation Tasks

1. Add confirmation command/event domain models and unit tests (`ConfirmProposalMessage`, `SelectCandidateMessage`, `SubmitCorrectionMessage`, `RequestRepeatMessage`, `CommunicationReadyEvent`, `RepeatRequestedEvent`, `ConfirmedPhraseSource`).
2. Extend `PeexhAgent` so that **all three** `AgentAction` outcomes (`PROPOSE_PHRASE`, `SHOW_CANDIDATES`, `REQUEST_REPEAT`) transition the agent to `AWAITING_CONFIRMATION`. Remove any path that transitions `REQUEST_REPEAT` directly to `IDLE`.
3. Add `confirm`, `select_candidate`, `submit_correction`, and `request_repeat` methods to `PeexhAgent`; test every valid and invalid transition, including that `request_repeat` is the only user action that returns to `IDLE` from `AWAITING_CONFIRMATION`.
4. Extend `/ws/speech` to parse all four confirmation control messages, keep the socket alive during `AWAITING_CONFIRMATION`, and emit `communication_ready` or `repeat_requested`; add WebSocket integration tests covering all paths including LOW confidence.
5. Extend `useSpeechStream` with typed confirmation state, pending actions, WebSocket send methods for all four controls, and lifecycle cleanup without closing after `agent_decision`.
6. Replace preview-only decision content in `TranscriptView` with the accessible controls described in Section 6.1, including the correct `REQUEST_REPEAT` UX (speak-again vs. manual entry).
7. Add a confirmed-message component with browser TTS and replay control, respecting the frontend feature flag.
8. Run backend tests and the frontend build, perform a manual browser flow covering all three confidence paths end-to-end, and update the changelog.

---

## 8. Acceptance Criteria

1. No `agent_decision` produces a communication-ready phrase without an explicit user action.
2. **All three** `agent_decision` action types (`PROPOSE_PHRASE`, `SHOW_CANDIDATES`, `REQUEST_REPEAT`) transition the agent to `AWAITING_CONFIRMATION`. The agent never exits `AWAITING_CONFIRMATION` autonomously.
3. For `REQUEST_REPEAT`: the frontend renders a speak-again prompt and a manual-entry option. "Speak again" sends `request_repeat` → `IDLE`; "Enter manually" sends `submit_correction` → `CONFIRMED`. No unverified phrase is presented as communicable.
4. The backend rejects stale, invalid, and out-of-state confirmation messages without changing agent state.
5. `communication_ready` contains only a user-confirmed, selected, or entered phrase and transitions the agent to `CONFIRMED`.
6. `repeat_requested` is emitted only in response to an explicit `request_repeat` message from the client.
7. Correction text remains session-only; no database, memory store, or persistence layer is added.
8. The confirmed phrase is displayed in large, readable text and is only spoken after the user activates browser TTS.
9. All new code, tests, comments, and documentation are in English.
10. Backend tests and the frontend production build pass.

---

## 9. Supersession

This RFC extends RFC-003 by defining the user-resolution path from `AWAITING_CONFIRMATION` to `CONFIRMED` or `IDLE`. It does not supersede RFC-003's deterministic scoring policy, interpreter abstraction, or agent action contract.
