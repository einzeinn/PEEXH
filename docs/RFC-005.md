# RFC-005 — Personal Speech Memory and Adaptive Learning Loop

**Status:** Proposed  
**Type:** Architecture / Feature / Database Schema  
**Scope:** Backend (`backend/app/memory/`), Supabase Database, LLM Context Injection, and Frontend UI Indicators  
**Governing Phase:** Phase 4 (Personal Speech Memory)  

---

## 1. Summary

This RFC implements **Phase 4: Personal Speech Memory** of the PEEXH roadmap. It introduces persistent, personalized speech adaptation without retraining underlying models.

The feature provides:
1. **Persistent Speech Memory Storage**: Storing verified user corrections (`raw_transcript` $\rightarrow$ `corrected_phrase`) and recurring phrase frequencies in Supabase PostgreSQL.
2. **Memory Retrieval & Similarity Matching**: Querying historical correction pairs via semantic vector search (`pgvector`) with deterministic lexical/trigram fallback before LLM interpretation.
3. **Memory-Aware LLM Prompting**: Injecting relevant personal memory matches into the LLM interpreter context to guide candidate generation toward the speaker's known vocabulary and habits.
4. **Deterministic Confidence Scorer Activation**: Dynamically setting `has_memory_match=True` in `ConfidenceScorer` when a retrieved pattern matches the current transcript, unlocking the $+0.10$ confidence bonus.
5. **Continuous Learning Loop**: Automatically recording confirmed corrections (`submit_correction`) and tracking communication frequency (`confirm_proposal`, `select_candidate`) without disrupting realtime latency.
6. **Transparent Frontend Memory Indicators**: Providing subtle, accessible UI cues in `TranscriptView` when personal memory informed an interpretation.

---

## 2. Motivation

Dysarthric speech varies significantly across individuals, but remains **highly consistent for an individual speaker**:
- A speaker with spastic dysarthria might consistently slur or drop final plosive consonants (e.g., saying *"wtr"* or *"wa-er"* for *"water"*).
- General speech-to-text models (including AssemblyAI) will repeatedly produce the same phonetic transcript errors for that speaker.

Without personal memory, PEEXH must re-interpret every distorted utterance from zero context, often settling in `MEDIUM` or `LOW` confidence. 

With **Personal Speech Memory**:
1. When a user corrects *"i ned wtr"* to *"I need water"*, PEEXH records the association.
2. The next time the user says *"i ned wtr"*, memory retrieval immediately identifies the verified pattern.
3. The LLM prioritizes *"I need water"*, and the confidence scorer awards the memory match bonus.
4. What was previously a multi-candidate selection (`SHOW_CANDIDATES`) becomes an immediate, single-tap confirmation (`PROPOSE_PHRASE`).

> **Core Principle Alignment:**  
> *"LLM interprets. PEEXH decides. User controls. Memory personalizes."*

---

## 3. Scope and Non-Goals

### In Scope
- PostgreSQL database schema migrations for Supabase (`speech_corrections`, `phrase_frequencies`).
- Vector similarity search (`pgvector`) and exact/trigram string matching fallback.
- `MemoryStore` abstract base class and factory pattern:
  - `SupabaseMemoryStore` (production/cloud).
  - `MockMemoryStore` (in-memory for unit tests, offline development, and fallback when Supabase is not configured).
- Retrieval injection into `Interpreter.interpret(transcript, stt_confidence, context, memory_matches)`.
- Automatic memory persistence hooks in `PeexhAgent` upon user confirmation actions (`submit_correction`, `confirm_proposal`, `select_candidate`).
- Activation of `has_memory_match` in `ConfidenceScorer`.
- Accessible badge indicator in the frontend (`"Learned from your speech"`).
- Unit and integration tests covering memory storage, retrieval, and scorer bonus.

### Out of Scope
- Raw audio waveform storage or acoustic voice biometric profiling (prohibited for user privacy).
- Global or cross-user model fine-tuning (each user's speech memory remains isolated).
- Complex multi-tenant auth / caregiver portals (V1 uses session or single-profile ID).
- Cloud vector database vendors outside Supabase (e.g. Pinecone, Qdrant).

## 4. Architecture & Data Flow

```text
1. Speech Stream Stops
      ↓
2. Raw Transcript ("i ned wtr", conf=0.68)
      ↓
3. MemoryStore.retrieve_matches(transcript)
      ↓
   Found match: "i ned wtr" -> "I need water" (freq: 3)
      ↓
4. Interpreter.interpret(transcript, context, memory_matches)
      ↓
   Candidates: ["I need water" (0.92), "I need winter" (0.45)]
      ↓
5. ConfidenceScorer.score_and_decide(has_memory_match=True)
      ↓
   Score = (0.35 * 0.68) + (0.65 * 0.92) + margin_bonus(0.05) + memory_bonus(0.10) = 0.98 -> HIGH
      ↓
6. AgentDecision (action=PROPOSE_PHRASE, primary="I need water")
      ↓
7. User confirms / corrects
      ↓
8. Learning Hook: MemoryStore.record_correction() / record_usage()
```

## 5. Technical Specification

### 5.1 Database Schema (Supabase PostgreSQL)

Migrations are defined in SQL and applied to the database specified by `DATABASE_URL` or Supabase REST API:

```sql
-- Enable necessary extensions
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- Optional: enable pgvector if available
-- CREATE EXTENSION IF NOT EXISTS vector;

-- 1. Speech Correction Pairs Table
CREATE TABLE IF NOT EXISTS speech_corrections (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id TEXT NOT NULL DEFAULT 'default_user',
    raw_transcript TEXT NOT NULL,
    corrected_phrase TEXT NOT NULL,
    frequency INT NOT NULL DEFAULT 1,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_corrections_user_raw 
ON speech_corrections (user_id, raw_transcript);

CREATE INDEX IF NOT EXISTS idx_corrections_trgm 
ON speech_corrections USING gin (raw_transcript gin_trgm_ops);

-- 2. Phrase Frequencies Table (Vocabulary reinforcement)
CREATE TABLE IF NOT EXISTS phrase_frequencies (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id TEXT NOT NULL DEFAULT 'default_user',
    phrase TEXT NOT NULL,
    use_count INT NOT NULL DEFAULT 1,
    last_used_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_user_phrase UNIQUE (user_id, phrase)
);

CREATE INDEX IF NOT EXISTS idx_phrase_freq_user_count 
ON phrase_frequencies (user_id, use_count DESC);
```

### 5.2 Domain Models (`backend/app/models/memory.py`)

```python
from pydantic import BaseModel, Field
from typing import List, Optional
from datetime import datetime

class CorrectionRecord(BaseModel):
    """A verified association between raw STT output and intended phrase."""
    id: Optional[str] = None
    user_id: str = "default_user"
    raw_transcript: str
    corrected_phrase: str
    frequency: int = 1
    created_at: Optional[datetime] = None

class MemoryMatch(BaseModel):
    """A retrieved memory candidate relevant to the active utterance."""
    matched_phrase: str
    original_transcript: str
    similarity_score: float = Field(ge=0.0, le=1.0)
    frequency: int = 1
    source: str = "correction"  # "correction" | "frequent_phrase"

class MemoryContext(BaseModel):
    """Container for memory matches passed into interpretation."""
    matches: List[MemoryMatch] = Field(default_factory=list)
    has_match: bool = False
```

### 5.3 Storage Abstraction (`backend/app/memory/`)

Following `TD-012` (Provider Interfaces), memory management is fully encapsulated behind an abstract interface:

```text
backend/app/memory/
├── __init__.py      # Exports MemoryStore, get_memory_store, models
├── base.py          # Abstract Base Class: MemoryStore
├── supabase.py      # Supabase/PostgreSQL implementation
├── mock.py          # In-memory dictionary implementation for tests/offline
└── factory.py       # Factory returning Supabase or Mock store based on config
```

#### Abstract Interface (`backend/app/memory/base.py`)

```python
from abc import ABC, abstractmethod
from typing import List
from app.models.memory import MemoryMatch

class MemoryStore(ABC):
    """Interface for personal speech memory retrieval and persistence."""

    @abstractmethod
    async def retrieve_matches(
        self,
        transcript: str,
        user_id: str = "default_user",
        limit: int = 3,
    ) -> List[MemoryMatch]:
        """Search memory for correction pairs matching the raw transcript."""
        pass

    @abstractmethod
    async def record_correction(
        self,
        raw_transcript: str,
        corrected_phrase: str,
        user_id: str = "default_user",
    ) -> None:
        """Persist or increment frequency for a user-verified correction pair."""
        pass

    @abstractmethod
    async def record_phrase_usage(
        self,
        phrase: str,
        user_id: str = "default_user",
    ) -> None:
        """Increment usage count and update last_used timestamp for a confirmed phrase."""
        pass

    @abstractmethod
    async def clear_memory(self, user_id: str = "default_user") -> None:
        """Erase stored speech memory for privacy compliance."""
        pass
```

### 5.4 Integration with LLM Interpreter

When `matches` are found, `app/llm/prompts.py` expands the interpretation context:

```text
User Speech Transcript: "{transcript}"
STT Acoustic Confidence: {stt_confidence}

Relevant Personal Speech Memory:
- Previously, when the user said "{orig}", they meant: "{phrase}" (used {freq} times)

Instruction:
Give strong weight to verified personal speech memory if the phonetic pattern is plausible.
```

### 5.5 Integration with Scorer & Orchestrator

1. **Before LLM Call**:
   ```python
   # In PeexhAgent.process_transcript()
   memory_matches = await self.memory_store.retrieve_matches(transcript)
   has_memory_match = len(memory_matches) > 0 and memory_matches[0].similarity_score >= 0.75
   
   interpretation = await self.interpreter.interpret(
       transcript=transcript,
       stt_confidence=stt_confidence,
       context={"memory_matches": memory_matches},
   )
   
   decision = self.scorer.score_and_decide(
       interpretation=interpretation,
       has_memory_match=has_memory_match,
   )
   ```

2. **After Confirmation (`Learning Hook`)**:
   ```python
   # In PeexhAgent.submit_correction(phrase)
   await self.memory_store.record_correction(
       raw_transcript=self.last_raw_transcript,
       corrected_phrase=trimmed,
   )
   
   # In PeexhAgent.confirm_proposal() / select_candidate(phrase)
   await self.memory_store.record_phrase_usage(phrase=phrase)
   ```

## 6. Privacy, Security & Data Retention

1. **No Audio Stored**: PEEXH never saves raw audio frames, MP3s, or WAV files. Only text transcripts and verified corrections are retained.
2. **User Isolation**: All database operations include `user_id`. Supabase Row Level Security (RLS) restricts read/write access.
3. **Data Sovereignty**: The user can reset or erase their personal speech memory at any time via `clear_memory()`.
4. **Offline / Mock Mode**: If `ENABLE_PERSONAL_MEMORY=false` or Supabase credentials are not provided, PEEXH automatically falls back to `MockMemoryStore` (in-memory, volatile session store), ensuring zero external data leakage.

## 8. Acceptance Criteria

1. **Learning Verification**: Submitting a correction for utterance $A \rightarrow B$ stores the correction pair. A subsequent utterance of $A$ retrieves $B$ with `has_memory_match=True`.
2. **Score Impact**: A valid memory match increases the composite confidence score by $+0.10$ through `ConfidenceScorer.score_and_decide`.
3. **Graceful Fallback**: If Supabase credentials are missing or unreachable, the system automatically falls back to `MockMemoryStore` without raising unhandled exceptions or breaking realtime transcription.
4. **Privacy Protection**: No audio files or raw waveforms are stored. Memory consists strictly of text string pairs.
5. **Regression Safety**: All existing 43 backend tests and frontend `npm run build` continue to pass.
6. **Language**: All code, migrations, tests, and documentation are strictly in English.
