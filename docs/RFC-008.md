# RFC-008 — Demo Polish, Presentation Flow, and Hackathon Submission Readiness

**Status:** Proposed  
**Type:** Presentation / Accessibility / UI Polish / Deployment  
**Scope:** Frontend UI (`frontend/`), Demo Dataset Simulation, Presentation Storyboard, and Deployment Configuration  
**Governing Phase:** Phase 7 (Demo Polish)  

---

## 1. Summary

This RFC implements **Phase 7: Demo Polish** of the PEEXH roadmap. It prepares PEEXH for high-impact demonstration, public deployment, and competition submission for the AssemblyAI Voice Agent Hackathon on lablab.ai.

The document specifies:
1. **Interactive Demo Mode & Audio Simulation Path**: An accessible, zero-risk fallback demonstration path enabling evaluators and judges to test PEEXH with pre-recorded/simulated dysarthric audio samples directly from the UI without requiring an active microphone or live AssemblyAI API key.
2. **Final UI & Accessibility Polish**: Fine-tuning visual aesthetics, typography, state transitions, contrast ratios, and touch targets to meet WCAG 2.1 AAA accessibility standards and eliminate UI jitter during streaming transcription.
3. **Sub-3-Minute Video Demo Storyboard**: A timed scene-by-scene script (problem $\rightarrow$ product $\rightarrow$ real-time AssemblyAI integration $\rightarrow$ personal memory learning $\rightarrow$ safety under uncertainty $\rightarrow$ output).
4. **Architecture Visuals & Presentation Assets**: Diagrams and infographics illustrating the "LLM interprets. PEEXH decides. User controls. Memory personalizes." paradigm.
5. **Production Deployment Readiness**: Streamlined configuration for cloud hosting (e.g. Vercel for frontend, Render/Railway/Fly.io for backend, Supabase for PostgreSQL persistence).

---

## 2. Motivation

A technically sound voice assistant can still fail if:
- Network instability or acoustic interference during a live video recording causes AssemblyAI WebSocket drops.
- Judges reviewing the repo locally lack an active AssemblyAI credit balance or microphone permissions.
- The UI feels unpolished, clinical, or overly complex for individuals with motor and speech disabilities.
- The demonstration video wanders without clearly proving the core value proposition within the strict 3-minute hackathon window.

Phase 7 resolves these risks by providing a resilient, polished presentation layer and an interactive demo mode that guarantees a flawless presentation under all conditions.

> **Core Principle Alignment:**  
> *"LLM interprets. PEEXH decides. User controls. Memory personalizes."*  
> Demo Polish ensures this principle is effortlessly understood in under three minutes.

---

## 3. Scope and Non-Goals

### In Scope
- **Interactive UI Demo Mode**: A toggleable "Demo / Sample Mode" in the frontend allowing judges to click representative dysarthric speech sample buttons (e.g., *"i ned wtr"*, *"am hungri"*, *"wer iz pil"*) to demonstrate real-time streaming, interpretation, confirmation, and memory learning without acoustic microphone access.
- **UI & Motion Polish**:
  - Enhanced state banners (`LISTENING`, `TRANSCRIBING`, `INTERPRETING`, `CONFIRMED`) with smooth CSS micro-animations.
  - Improved touch target sizing ($\ge 80\text{px}$) and focus states for motor accessibility.
  - Large-text mode optimization for `ConfirmedMessageView`.
- **Demo Storyboard & Script (`docs/demo/` or `docs/04-Hackathon.md`)**:
  - Precise 0:00–2:50 minute breakdown matching hackathon judging criteria.
  - Split-screen recording guidelines (video/audio input vs PEEXH interface).
- **Architecture Visual Asset**: High-resolution Mermaid/SVG architecture visual comparing raw STT vs PEEXH agent loop for demo video inclusion.
- **Deployment Manifests**: Dockerfile / Procfile and environment checklists for public cloud hosting.

### Out of Scope
- Native iOS/Android packaging (V1 remains a mobile-first responsive PWA/web application).
- Multilingual translation or accent localization (V1 remains English-first).
- Caregiver authentication portals or clinical telemetry dashboards.
- Modifying core scoring equations or memory schemas established in RFC-003 and RFC-005.

## 5. Technical Specification

### 5.1 Interactive Demo Panel (`frontend/src/components/demo/DemoBar.tsx`)

To ensure any evaluator can test the application instantly without microphone access, an optional `DemoBar` component will be embedded at the top of the interface:

- **Visibility**: Toggleable via an accessible button or `?demo=true` query parameter.
- **Pre-set Buttons**:
  1. `Sample 1: "i ned wtr"` $\rightarrow$ Triggers high-confidence phrase proposal (*"I need some water"*).
  2. `Sample 2: "wer iz pil"` $\rightarrow$ Demonstrates medium-confidence candidates with inline correction option.
  3. `Sample 3: "uh ..."` $\rightarrow$ Demonstrates safe low-confidence fallback (`REQUEST_REPEAT`).
  4. `Sample 4: Memory Loop Demo` $\rightarrow$ Demonstrates two-step learning: submit correction for *"wer iz pil"* $\rightarrow$ next utterance immediately proposes *"Time for my medicine"*.

### 5.2 Frontend UI & Aesthetic Polish

Following `docs/08-Design.md`:
1. **Color Palette**: Calm, non-clinical palette (slate neutrals, vibrant accessible indigo `#4F46E5` primary, emerald `#059669` for confirmation, amber `#D97706` for candidates).
2. **Typography**: Google Fonts Inter or system sans-serif with distinct tracking and legible line-height.
3. **Contrast Compliance**: Verify all text elements meet minimum contrast ratio of 7:1 for normal text and 4.5:1 for large text (WCAG AAA).
4. **State Transition Animation**: Subtle pulse animation on `TapToTalkButton` when active, with smooth layout transitions (CSS `transition-all duration-200`) when candidates expand.

| Timestamp | Scene | Visual | Audio / Narration |

### 5.4 Production Deployment Architecture

- **Frontend**: Next.js App Router deployed on Vercel or cloud static host with environment variable `NEXT_PUBLIC_WS_URL`.
- **Backend**: FastAPI deployed via containerized Dockerfile or ASGI service with WebSocket support enabled.
- **Database**: Cloud Supabase PostgreSQL with `speech_corrections` and `phrase_frequencies` tables created via `001_create_memory_tables.sql`.

## 6. Accessibility & Human Factors

1. **Physical Accessibility**: No hold-to-talk, no swipe gestures, minimum touch target $\ge 80\text{px} \times 80\text{px}$ for the main button, and $\ge 48\text{px}$ for candidate buttons.
2. **Cognitive Load**: At no point does the user see more than 3 candidate choices simultaneously.
3. **Sensory Output**: Visual confirmation banner (high contrast 48px font) combined with auditory SpeechSynthesis TTS playback for face-to-face communication partners.

## 8. Acceptance Criteria

1. **Interactive Demo Functional**: Evaluators can click sample buttons in the frontend and observe full end-to-end interpretation, scoring, confirmation, and memory learning without microphone input.
2. **Accessibility Verification**: All interactive buttons maintain minimum $48\text{px} \times 48\text{px}$ touch targets ($80\text{px}+$ for speak button), visible focus indicators, and meet WCAG 2.1 AAA contrast requirements.
3. **Sub-3-Minute Video Script**: A complete scene-by-scene script with timestamps totaling under 2 minutes 50 seconds is documented in `docs/13-DemoScript.md`.
4. **Clean Production Build**: Both `npm run build` (frontend) and pytest suite (64/64 tests) continue to pass with zero errors.
5. **Deployment Artifacts**: Complete Docker/container configuration provided for backend deployment with documented environment variables.
6. **Language**: All UI text, scripts, code comments, and documentation are strictly in English.
