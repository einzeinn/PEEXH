# RFC-001 — Repository Bootstrap and Development Governance

**Status:** Accepted  
**Type:** Foundation / Governance  
**Scope:** Repository-wide

## 1. Summary

This RFC establishes the initial PEEXH repository structure, architecture boundaries, development rules, and documentation-first workflow.

It also defines the first implementation task for any coding agent entering the repository.

## 2. Motivation

PEEXH is intentionally narrow.

Coding agents are useful for execution but can easily:
- expand scope;
- add unnecessary frameworks;
- mix frontend/backend concerns;
- hardcode provider details;
- modify architecture without updating documentation.

This RFC creates explicit boundaries before implementation begins.

## 4. Governance Rule

Before implementing any non-trivial change, the agent must ask:

> Does this change alter product behavior, architecture, data, provider strategy, API contracts, safety policy, accessibility behavior, or scope?

If yes:
1. update the relevant document;
2. create a new RFC when the decision is substantial or cross-cutting;
3. only then implement.

## 5. Changes That Require Documentation First

Examples:
- new core feature;
- state-machine change;
- confidence-policy change;
- memory-schema change;
- provider replacement;
- database change;
- new major dependency;
- new architecture layer;
- new API contract;
- accessibility behavior change;
- privacy behavior change.

## 6. Changes That Usually Do Not Require a New RFC

Examples:
- typo;
- local visual polish;
- lint fix;
- dependency patch update with no behavior change;
- narrowly scoped bug fix;
- test-only improvement;
- documentation formatting.

Relevant documentation should still be updated if behavior materially changes.

## 7. Architecture Decision

Frontend and backend remain separate.

### Frontend
Next.js + TypeScript.

Owns:
- microphone UX;
- application states;
- candidate display;
- confirmation;
- correction;
- communication output UI;
- accessibility.

### Backend
FastAPI + Python.

Owns:
- AssemblyAI connection;
- agent state;
- LLM interpretation;
- confidence scoring;
- memory;
- persistence;
- API contracts.

## 8. Configuration Decision

All deploy-time/provider-specific configuration must be environment driven.

`.env` contains configuration values.

Python virtual environment is located at:

```text
backend/.venv/
```

and must be ignored by Git.

## 9. Modularity Decision

Implement replaceable interfaces for:
- speech transcription;
- interpretation;
- memory;
- scoring;
- speech output.

Avoid direct provider coupling in core domain logic.

## 10. Agent Framework Decision

Do not introduce LangChain, LangGraph, multi-agent systems, or similar frameworks in the initial implementation.

PEEXH V1 uses a custom explicit state machine.

## 11. First Coding-Agent Task

The first coding agent should:

1. Read:
   - `README.md`
   - `.agent/rules.md`
   - `docs/00-ProductPrinciples.md`
   - `docs/02-PRD.md`
   - `docs/06-Architecture.md`
   - `docs/07-TechnicalDecisions.md`
   - this RFC.

2. Create the minimum frontend and backend project scaffolds without implementing speculative product features.

3. Frontend scaffold:
   - Next.js;
   - TypeScript;
   - Tailwind;
   - accessible base layout;
   - no complex product UI yet.

4. Backend scaffold:
   - FastAPI;
   - typed settings/config;
   - health endpoint;
   - module directories defined by architecture;
   - no provider-specific business logic outside adapters.

5. Add:
   - `.env.example` files;
   - test scaffolding;
   - local development instructions.

6. Verify:
   - frontend starts;
   - backend starts;
   - backend tests run;
   - secrets are not committed.

7. Update `docs/12-Changelog.md` after successful bootstrap.

## 12. Forbidden Work in RFC-001

The first task must **not**:
- build the full agent;
- add authentication;
- create a caregiver dashboard;
- add translation;
- add emergency integration;
- add analytics;
- introduce a general agent framework;
- build production-scale infrastructure;
- create unused abstractions.

## 13. Acceptance Criteria

RFC-001 is complete when:
- repository structure exists;
- frontend and backend start independently;
- environment configuration is documented;
- architecture boundaries are reflected in code;
- tests can run;
- no secret is committed;
- no out-of-scope feature was added.

## 14. Superseding This RFC

Any future RFC may supersede specific decisions here, but it must explicitly state what it replaces and why.
